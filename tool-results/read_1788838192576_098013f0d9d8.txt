   276→### Important Observations:
   277→
   278→1. **No migrations tracked.** Using `prisma db push --accept-data-loss` — no migration history, no rollback capability.
   279→2. **No indexes** defined beyond `@unique` and `@id`. No composite indexes for common queries (e.g., `organizerId + status`).
   280→3. **EventTag seeding is missing** — tags are created but never linked to events.
   281→4. **No `REJECTED` status** in Event model — only DRAFT, PENDING, PUBLISHED, CANCELLED, COMPLETED. Admin "reject" sets CANCELLED.
   282→5. **No `OrganizerProfile` model** — organizer info (company, website, social) is not separated from User.
   283→6. **No `EventSchedule`/`Session` model** — no multi-session/multi-day event support.
   284→7. **No `Speaker`/`Artist` model** — no speaker/artist management.
   285→8. **No `Favorite`/`Bookmark` model** — no event favoriting.
   286→9. **No `DiscountCode`/`PromoCode` model** — no promo/discount support.
   287→10. **No `AuditLog` model** — no audit trail for admin actions.
   288→11. **No `Refund` model** — no refund tracking.
   289→12. **No `TicketTransfer` model** — no ticket resale/transfer.
   290→13. **No `EmailTemplate` model** — no email notification templates.
   291→14. **No `Country`/`City` model** — location is just free text fields.
   292→15. **`features` on SubscriptionPlan is a JSON string**, not a separate table — limits querying.
   293→16. **Payment `transactionId` has no unique constraint** — could have duplicates.
   294→17. **No soft-delete pattern** — only User has `isActive`, all other deletes are hard deletes.

   460→| 7 | 🟠 HIGH | **Ad PATCH/DELETE has no ownership check** | Data manipulation |
   461→| 8 | 🟠 HIGH | **Ticket check-in has no event ownership check** | Unauthorized check-ins |
   462→| 9 | 🟠 HIGH | **Admin can grant SUPER_ADMIN to anyone** | Privilege escalation |

   464→| 11 | 🟠 HIGH | **No 401 auto-logout in client** | Stale sessions persist |

   658→## 10. SaaS Architecture Assessment
   659→
   660→### Current State: ❌ NOT Properly SaaS
   661→
   662→The current architecture does **not** properly support multiple event organizers as separate SaaS customers.
   663→
   664→### Issues:
   665→
   666→1. **No subscription enforcement.** Plans exist in the database but nothing checks whether an organizer has exceeded their plan limits (max events, max tickets). An organizer on the Free plan can create unlimited events.
   667→
   668→2. **No billing system.** No Stripe integration, no payment collection, no invoice generation, no usage-based billing.
   669→
   670→3. **No data isolation.** All organizers share the same database tables with no row-level security or tenant isolation. Admin can see all data. An organizer cannot be restricted to only their data at the DB level.
   671→
   672→4. **No plan-based feature gating.** Features like "Custom branding," "API access," or "Advertisement slots" listed in plan features are not checked anywhere.
   673→
   674→5. **No organizer onboarding.** No step-by-step setup, no profile completion, no verification.
   675→
   676→6. **No usage tracking.** No mechanism to count events created this month, tickets sold, API calls made, etc.
   677→
   678→### What Would Be Needed:
   679→
   680→| Component | Status | Description |
   681→|-----------|--------|-------------|
   682→| Subscription model | ❌ Missing | Stripe Customer + Subscription webhooks |
   683→| Plan limit enforcement | ❌ Missing | Middleware checking plan limits before event creation |
   684→| Usage tracking | ❌ Missing | Monthly counters for events, tickets, API calls |
   685→| Billing/invoicing | ❌ Missing | Stripe Billing + invoice PDF generation |
   686→| Feature flags | ❌ Missing | Per-plan feature gate checks |
   687→| Tenant isolation | ⚠️ Partial | Application-level filtering exists (organizerId), no DB-level isolation |
   688→| Organizer profiles | ❌ Missing | Separate public-facing organizer pages |
